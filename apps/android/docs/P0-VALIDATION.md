## 锁屏收件失败诊断

- 用户观察：系统短信应用有测试消息，SIMLink 无对应记录。
- ADB 证据：应用进程仍存在；stopped=false；RECEIVE_SMS 已授予且 AppOps allow。当前进程 AndroidRuntime/SQLite 错误日志未见异常。
- ActivityManager 广播历史：SMS_RECEIVED 对本应用 SmsReceiver 的投递标为 `SKIPPED`，原因 `Greezer Denial`。此证据支持本次广播在进入接收器前被系统后台管控拒绝，不据此推断所有漏收均为此原因。
- 不使用全局禁用优化、私有 API 或自动授权绕过。建议用户只修改 SIMLink 单应用省电策略为无限制，保持其他设置不变，再用新测试消息复测。随后用户报告“现在收到了”。记录为按此指引复测后短时锁屏收件成功；设置未通过 ADB 独立读取确认，不外推为长期后台可靠性。
- 没有通过代理更改系统设置，没有读取或提交短信正文、号码及完整系统日志。

## 发件系统确认框 · 已定位组件，免确认路径未验证

用户报告真实发件成功，但发送过程中出现系统级确认框。尚未确定这是首次运行时权限、厂商逐次发送授权、特殊号码提示或其他机制；不从一次现象推断原因。不绕过确认。先核对文案及是否存在系统提供的持续授权选项，再评估远程无人值守发件可行性。

用户补充确认框文案：询问是否允许应用发送，并显示收件人与内容，按钮为取消/确认发送，没有记住选择选项。属于逐条内容确认的表现，而非普通运行时权限提示。尚不能确认后续每次必然弹出或系统设置是否提供持续允许选项；无人值守发件仍未通过。尝试进一步检查时 ADB 无连接设备，未能读取当前 SEND_SMS AppOps。

进一步只读检查：设备为 HyperOS OS3.0.306.0.WOPCNXM；SEND_SMS runtime permission 已授予，标准 AppOps 为 allow，默认 SMS 角色持有者为系统短信 com.android.mms。源码直接调用 SmsManager，不创建发送确认 Dialog。这排除了普通 SEND_SMS 未授权作为当前唯一原因；系统额外确认的所属组件和持续授权入口仍待核实。未修改 AppOps、角色或系统安全设置。

用户再次触发发送并将确认框保持打开后，ADB 的 `topResumedActivity` 显示 `com.miui.securitycenter/com.miui.permcenter.ctaverify.SendSmsVerificationActivity`。同时标准 `SEND_SMS` AppOps 仍为 `allow`。因此本次弹窗已确定来自小米安全中心，且在第二次测试仍出现；不能以普通发送权限已允许推断无人值守可用。检查仅读取组件及权限元数据，没有读取收件人或正文、点击确认或触发新发送。

本机当前非默认短信应用路径的无人值守发送仍受阻。没有证据证明默认短信角色可以免除此确认，也未找到适用于此系统版本的官方持续允许配置说明；不把 Activity 名称中的 `ctaverify` 当成法规或豁免规则的证据。后续若评估默认角色，应先完成角色职责，再单独实测；接收闭环可以独立推进，不能把本机远程发件标为可用。

用户后续决定：此定制系统问题只记录，不继续定位免确认设置或专门适配；推进 P1。此决定不改变“本机无人值守发件未通过”的验证事实，也不要求为该机型立刻实现默认短信角色。
