### 建议推进顺序

1. **P1 验收并保存 Git 基线。** 验证扫码后返回、真实测试短信端到端、断网补传且不重复、短时锁屏与重启后恢复、解绑后凭证失效/条目移除/历史保留。自然心跳另记录，不用 ADB 强制触发替代。检查现有未提交改动、敏感文件排除后形成阶段提交。
2. **收件体验补齐。** 建立 SIM 清单、用户命名与映射变化规则；添加服务端已读记录及跨浏览器同步，再实现验证码候选与单独复制。当前追加消息游标不会返回旧消息的已读变化，须同时设计阅读状态刷新接口/游标，不能只改页面标记。
3. **安装型 PWA 与 iPhone 验证。** 补 manifest、图标、静态外壳缓存和升级提示；不缓存短信 API。使用主机已有 HTTPS 代理验证添加主屏幕、关闭重开、网络恢复和登录持久性，不增加 Caddy 容器。
4. **P2 远程发送闭环。** 先明确命令/幂等/过期/领取/执行/回执及 SIM 校验，再接回复和新建 UI。小米逐条确认继续只记录，不将该机无人值守发送列为已通过。
5. **P3 通知及长期运行。** 独立 notifications/outbox 接 Web Push 和 Telegram，默认无正文；完成 72 小时试运行、升级备份恢复和发布准备。

设计继续沿用既定白蓝风格、SIM 下划线 tab、移动独立详情/桌面双栏；不再重新探索配色。下一轮设计验收针对真实功能的空态、失败、恢复、键盘与窄屏，Android 优先运行摘要、权限修复和配对生命周期。现有静态图与 demo 的发送/已读不代表生产能力。

## 产品定位

把留在 Android 手机上的 SIM，变成自己随时能访问的短信与来电信息入口。

- SIMLink Gateway：Android 留守端，负责设备配对、短信收发、能力检测、可靠同步。
- SIMLink：手机优先的 Web/PWA，负责阅读、发送、设备管理和通知配置。
- simlink-server：自托管服务，负责认证、存储、命令和可插拔通知。

主任务：收到验证码后快速查看并复制；偶尔从指定 SIM 发短信；知道留守设备什么时候失联。

## 初始假设与待确认事项

已确认：用户留守手机已从 Android 14 升级到 Android 16；项目计划开源，优先保持较低维护成本，不兼容过老 Android。

先按个人自用、单管理员、自托管、Android APK 安装、iPhone 为主客户端设计。一台 Android 连接一个后端；数据结构支持多个设备和每台设备的多张 SIM。先验证用户的 Android 16 设备，再扩大兼容范围。

待确认：留守手机具体型号、运营商和双卡情况、部署位置及 HTTPS 条件、来电功能的优先级。初期建议 GitHub Releases 分发 APK，暂不将 Google Play 上架列为发布条件。当前不因这些信息缺失停止产品规划。

## 开源与低维护成本策略

- 建议最低 Android 14，即 minSdk 34；不为 Android 13 及更老版本添加兼容分支。不设置 maxSdk，较新版本经过验证后进入兼容清单。
- minSdk 与 targetSdk/compileSdk 分开管理：后两者在实施时选择经过测试的稳定版本，按更新周期升级，不冻结在 34。
- 支持分级为“维护者真机验证”“社区验证”“尚未验证”；模拟器只能验证一部分应用行为，不能替代真实蜂窝收发和厂商后台测试。
- 维护一条主线和当前稳定版，原则上不维护多个历史版本分支。最低版本提升需提前说明，不能在小版本里悄悄淘汰 Android 14。
- 原生 Kotlin、官方 Android API；不加入 root、无障碍模拟点击、私有厂商 API 或远程操作系统设置等替代路径。
- 厂商省电设置以简短操作文档和社区验证条目处理；不承诺所有 Android 14+ 手机都能全天候后台运行。
- 单体后端、一种默认数据库、同源托管 PWA；单管理员、单节点部署优先。通知首版只维护 Web Push 与 Telegram。
- 初期直接发布签名 APK 和自托管部署包；保护发布签名密钥并明确升级路径。不开源任何真实 token、短信样本或部署凭证。
- 建议 MIT 作为低门槛开源许可证候选，正式发布前由维护者确定；本轮不替用户写入最终 LICENSE。
- 开源准备包含 README、安装升级/备份文档、兼容矩阵、贡献指南、问题模板及私密漏洞报告渠道。问题模板收集机型、系统、应用版本和脱敏日志，不要求公开短信正文。

## 必须先验证的技术边界

1. 短信角色与权限：评估默认短信应用路线及其完整职责，包括本地短信展示、发送及系统短信库写入；不能只申请角色却不实现角色要求。目标机实测普通短信和验证码、长短信、双卡、锁屏和重启。
2. 后台运行：确认目标系统可用的后台机制、启动限制及必要的用户设置。不能以“有前台服务/长连接”推导永远在线；强制停止后可能需要人工重新启动。
3. 来电：先验证能读取哪些状态及号码。若依赖默认电话应用，需承担拨号、来电及通话界面，不能把 InCallService 当成轻量监听器。
4. iOS 通知：针对主屏幕 Web App 做能力检测和用户主动授权引导；通知失败不能影响短信读取。服务端受理、设备显示、用户已读是不同事实。
5. 旧讨论中 Android 16/17 OTP 延迟的具体断言不直接作为设计依据；须按目标系统与官方文档另行确认。

## 系统结构建议

Android 本地持久队列 → 服务端事件入库 → PWA 增量同步 / 通知分发。

PWA 发送请求 → 服务端持久命令 → Android 领取与记录 → 调用短信接口 → 逐步上报结果。

建议起点：Android 使用 Kotlin 与原生 UI；后端采用单体服务与事务数据库；PWA 使用 TypeScript。后端语言按维护者熟悉程度确定，暂不为了规划引入微服务、消息中间件或多个数据库。

核心实体：User、Device、Sim、Message、Command、NotificationChannel、NotificationRule、DeliveryAttempt、PushSubscription、PairingSession。网页会话与设备凭证分离；通知订阅属于具体浏览器安装实例。

可靠性约束：

- 收件持久化后 ACK；设备 eventId 去重；补传保留原接收时间与同步时间。
- SIM 使用后端逻辑标识，Android subscriptionId 是当前映射，不当永久身份。拔卡、换卡或映射变化后暂停受影响的待发命令。
- 命令携带不可变目标 SIM、幂等键、有效期。Android 本地执行记录跨重启保存。
- 网络重试可以安全去重；蜂窝发送存在“已提交但回执丢失”窗口，不能承诺 exactly-once。此时呈现“结果未确认”，不自动重新发送。
- 长短信按分段跟踪；部分成功不能笼统显示失败后重发整条。
- 设备断线后补传历史短信，默认不逐条补发旧通知；按原接收时间与有效期抑制过时验证码提醒。
- 通知采用事务 outbox 与独立投递记录；短信已经保存不等于通知已送达。

## 数据与访问默认值

- 初始管理员通过部署时一次性凭证创建；登录后才能读取短信或生成配对码。
- 已确认产品要求：PWA 默认持久登录，同一安装实例关闭重开、手机重启或应用更新后不主动要求重新登录。建议采用服务端可撤销的持久会话与同源 HttpOnly/Secure Cookie，初始策略为 90 天不活跃过期、前台有效使用时滑动续期；具体时长可由部署配置调整。网页会话记录持久化，普通后端重启不使用户退出。
- 配对码建议 5 分钟有效、单次使用、限制尝试次数；二维码中不包含永久设备凭证。
- 扫码后展示目标服务器域名，由用户在 Android 上确认；TLS 与 API 兼容检查不能证明服务器值得信任。
- 设备凭证可撤销；Telegram Token 仅在服务端保存，前端后续仅显示掩码。
- 默认不向第三方通知正文；全文模式由用户主动开启并展示预览。
- 第一版服务端可处理正文，不声称端到端加密。若后续加入 E2EE，需重新定义服务端检索、验证码识别与 Telegram 全文通知。
- PWA Service Worker 默认仅缓存静态外壳，不缓存短信 API 正文；离线显示无法刷新，退出清理会话内数据。
- 保留周期在设置中明示；建议初始 30 天，可修改或手动清空。删除说明仅影响 SIMLink 数据，不自动删除手机短信；备份保留规则单独说明。
- 日志避免正文、验证码与 token；加密备份覆盖数据库和必要密钥，提供恢复验证流程。

## 试运行验收矩阵

- 普通短信、验证码、中文/Unicode、长短信、多段短信与双卡来源。
- 锁屏过夜、系统省电、网络切换、断网 30 分钟、Android 和后端重启。
- 设备被强制停止或权限被撤回：PWA 显示异常与最后活动时间，不伪装正常。
- 发件：双击提交、执行前过期、执行后回执断网、分段失败、换卡后待发命令。
- Web Push：未安装、授权拒绝、订阅失效、正常受理但用户未点击；Telegram 配置失败与恢复。
- 从通知进入短信，登录后返回原详情；短信已删除时给出明确提示。
- 在目标设备上进行至少 72 小时持续试运行，记录接收→入库→页面可见延迟分布、缺失与重复；这是发布门槛建议，不代表已验证。

## P1 服务端基础 · 2026-09-29

用户决定：小米定制系统发件确认仅作兼容记录，不继续专门调查或适配；P0 剩余未验证项保留，不阻塞下一阶段工程。
